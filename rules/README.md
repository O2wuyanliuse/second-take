# rules/ —— 规则层：形状与绑定分开

> 这一层解决的问题只有一句：**判据能不能脱离原项目存在？**
>
> 2026-11-11 之前，答案是「说不清」——17 项检查里，规则和项目参数搅在一起写，
> 谁也分不出哪一条是通用方法、哪一条只是碰巧长成通用样子。
> 现在把每条规则切成两半，切开就能看出来。

## 一条规则 = 两份文件

| 文件 | 装什么 | 能不能公开 |
|---|---|---|
| `<名>.rule.json` | **形状**：要哪些参数、每个参数什么意思、必填不必须 | **能**。里面没有一个项目词 |
| `<名>.bind.json` | **绑定**：本项目这些参数填什么值 | **不能**。填的是本项目的路径、词表 |
| `<名>.bind.example.json` | **空靶**：全留空，只演示怎么填 | 能 |

代码在 `_rule.py`。规则个数不写死——加一条规则＝加一份 `.rule.json` ＋ 在 `_rule.py` 的 `IMPL` 里挂一个实现函数。

## 三种结局，退出码不同

```
绿     已绑定，无违规        rc=0
红     已绑定，有违规        rc=1   逐条点名
未绑定 参数不齐              rc=2   逐条列出缺什么、去哪填
```

**「未绑定」是独立状态，不是绿。**

理由不是洁癖，是有过一次真事故：2026-11-10，公开仓的三组脱敏词表全是空的，
打包脚本读不到词表也没报错，于是**什么都没删，验包报「全绿」，带着项目组织名发了出去。**
空词表不会报错——它只会让每一份素材都显示「干净」。

所以这一层在退出码上就把「没查」和「通过」分开。**任何人看到 rc=2，就知道这一项没在保护他。**

## 用它

```bash
python rules/_rule.py --list                              # 有哪些规则、绑没绑
python rules/_rule.py 同一实体两种定性                      # 跑（用同目录的 .bind.json）
python rules/_rule.py 同一实体两种定性 --bind 别的.bind.json  # 换一份绑定跑
```

## 拿它去做你自己的项目

1. 复制 `rules/` 到你仓库根
2. `cp 同一实体两种定性.bind.example.json 同一实体两种定性.bind.json`
3. 照 `.rule.json` 里的 `params[].fill` 逐项填：两份源文件的相对路径、实体名正则、正负词表
4. 跑。**如果它报「未绑定」，那不是它坏了——是它诚实地告诉你：这一项现在什么都没查。**

## 三条铁律

1. **空靶不许算绿。** 参数不齐就是 rc=2，不许降级成「跳过＝通过」。
2. **抽出之后，原处必须改调，不许两份并存。** 这条是今天所有病的根：
   `_drift.py` 的 C4 抽到这里之后，原函数只留一层壳，旧实现和旧词表**全部删掉**。
   两份都留着，就等于又造了一对迟早要漂移的副本。
3. **`.rule.json` 里不许出现项目词。** 文件名、角色名、组织名一个都不许。
   判断办法：把它贴给一个没读过项目的人，他能不能照着填自己的项目？能，才合格。

## 现有的规则

| 规则 | 一句话 | 通用在哪 |
|---|---|---|
| `同一实体两种定性` | 同一件东西在两份权威源里的定性不许打架 | 任何长线项目都有多份「当前状态」文件 |

## 一条没做到的，写在这儿

`同一实体两种定性` 只证「两处说法一致」，**不证说法本身对**。两处都写错，它查不出来。
这是它的边界，不是 bug——**判据能证什么、不能证什么，写在规则文件里比写在人心里可靠。**
