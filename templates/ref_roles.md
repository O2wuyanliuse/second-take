# 参考图角色分工（通用 · 可整套复制到任何出图项目）

> **这份是通用层，不含任何项目专名。** 换项目时整份带走，一个字不用改。
> 项目自己的风格串与权重写在 `styles/<项目名>.style_lock.md`，提示词里原样引用，不在这里复写。
>
> **一句话**：一张参考图只准干一件事。写清它干哪件，写不清就别挂。

---

## 一、为什么要有这一层

出图失败里最常见的一类，不是提示词写得不美，是**参考图在偷偷兼职**。

一张挂着「人物参考」用的人像，模型会连它的画风一起吃掉；一张挂着「画风参考」用的场景图，模型会连它的构图一起吃掉。于是你写了一大段文字描述画风，出来还是不听话——**因为参考图的权重高于文字，这是平台机制，不是提示词水平问题**。

反过来也一样：文字里写死「表情中性、头不歪」，但挂的参考图是一张歪着头在笑的脸，模型会先记住「这个人在干什么」，再记住她长什么样。

所以参考图必须分工。分工的方式不是靠段落下意识写对，而是**每一张图都当场声明它负责什么，没声明的就是没有**。

---

## 二、四条角色

每条任务都写以下四行，**有哪张写哪张，没有就写「无」，整行不许省**。

**缩写怎么来的**（不用记，看一眼就够）：`CHAR` ＝ character（人物）／`STYLE` ＝ style（画风）／`PROP` ＝ property（影视里的“道具”）／`LAYOUT` ＝ layout（版式机位）；四个都以 `_REF` 结尾，`REF` ＝ reference（参考）。**它们不是模型的指令，是台账**——模型读到的是权重与文件名，读不到你的分类学。

```
CHAR_REF：只约束人物与服装
STYLE_REF：只约束画风——笔触、线宽、阴影、色数、色温
PROP_REF：只约束道具与场景
LAYOUT_REF：只约束构图与机位
```

| 角色 | 管什么 | **不管**什么 | 典型误用 |
|---|---|---|---|
| `CHAR_REF` | 脸型、五官、发型、发色、体型比例、服装版型与部件 | 画风、构图、光线 | 挂一张正脸去出三视图，结果三个视角都被拉成头肩构图 |
| `STYLE_REF` | 笔触粗细、线的存在方式、阴影是硬边还是渐变、用几层色、色温偏冷偏暖 | 长什么样、站在哪、怎么摆 | 挂一张人物图当画风参考，把那张脸和姿态一起带进来 |
| `PROP_REF` | 道具形制、材质、场景结构与陈设 | 人物、画风、机位 | 挂场景图取道具，结果整张图的机位被锁成那张场景的机位 |
| `LAYOUT_REF` | 构图、机位高度、景别、主体在画面中的位置与朝向 | 画风、服装细节、光影 | 挂一张构图完美的图，连它的画风一起继承 |

**写成一行就够，不要写成一段解释。** 声明是给自己和下游看的台账，不是给模型的修辞——模型读到的是权重与文件名，读不到你的分类学。

## 三、三条固定规则

### 规则 1：同一张图不能兼任两个角色

一张图只能进一个格子。

**为什么**：兼职的意思就是「它的全部特征都会进来」，包括你没打算要的那些。当你写「这张既当人物参考又当画风参考」时，你实际是在说「人物和画风都按它来」——那么凡是这张图上有的东西（姿态、构图、光线、背景色），全都获得了授权。

**违反会长成什么样**：挂一张人物立绘当画风参考，出来的人物穿着那件衣服、站在那个位置、打那个光。你以为改的是画风，实际改的是整张图。

**唯一例外**：如果这张图恰好就是「目标画风 + 目标人物」的成品（例如同一角色的上一版定妆图），它可以只当 `CHAR_REF`——**画风靠文字与 style_lock 去对齐，不许拿它当画风依据**。这条例外要写在声明旁边，不能默默用。

### 规则 2：禁止合并说法

不许写「参考这几张图」「参考以上素材」「综合参考图 1、图 2」。

**为什么**：合并说法等于放弃分工。模型收到的是「几张图，都参考」，它只能自己决定哪张管什么——而它决定的方式是按权重和画面显著性，不是按你的意图。

**违反会长成什么样**：三张参考图里，最亮、最完整、最像成品的那张会赢，其余两张变成配色提示。你以为在做加权，实际是在抽签。

**改成什么**：拆成四行声明，各就各位；同一角色需要两张时，在同一行里写明主次——`CHAR_REF：A 定脸，B 定服装版型`。**不是两张都当人物参考，是两张各自负责人物的不同部分。**

### 规则 3：平台只支持单层参考时，分两步走

有些平台一次只吃一张参考图，或者多图时会锁死构图。这时不要硬塞，拆成两步：

```
第一步 · 出风格底图
    PROP_REF / LAYOUT_REF：无（或只给场景）
    STYLE_REF：<style_lock 里那串，原样引>
    CHAR_REF：无
    → 产出一张只有画风、没有具体人物的底图

第二步 · 用底图 + 人物图二次生成
    STYLE_REF：第一步的产物
    CHAR_REF：<人物图>
    PROP_REF / LAYOUT_REF：按需
    → 产出一张既对风格、又对人的图
```

**两步都要写清哪一步干什么**，不能只写「先出底图再做」。第二步的提示词里要把第一步的产物明确标成 `STYLE_REF`，而不是笼统地「参考第一张」——否则第二步的底图会连构图一起锁进来。

**违反会长成什么样**：单层平台上硬挂两张，模型锁死第一张的构图，第二张只贡献一点颜色。你以为是双参考，实际是单参考加一次无效输入。

## 四、可直接复制的声明块

放在提示词最前面，参数行之下、正文之上：

```
参考图分工：
CHAR_REF：<文件名或「无」>
STYLE_REF：<文件名或 style_lock 引用，或「无」>
PROP_REF：<文件名或「无」>
LAYOUT_REF：<文件名或「无」>
```

需要写强度时写在文件名后面，不要另起一行：

```
CHAR_REF：role_face_v3.png（强度 35）
STYLE_REF：styles/<项目>.style_lock.md §一（照抄，不改写）
PROP_REF：无
LAYOUT_REF：无
```

## 五、机器怎么检查（CHECK-REF）

提交前自检里有一条 `CHECK-REF`，判四件事：

| 编号 | 判什么 | 不过时 |
|---|---|---|
| R1 | 四行声明齐不齐（缺行／写空／写成「参考这几张」） | **红，阻断提交** |
| R2 | 同一文件名是否出现在两行 | **红，阻断提交** |
| R3 | 正文里有没有「参考这几张图」这类合并说法 | **红，阻断提交** |
| R4 | 写了「平台只支持单层」却没有两步描述 | 提示，不阻断 |

**存量文件**：迁移前的老提示词可以登记进豁免名单，报「未迁移」不阻断。豁免是**清单式**的，写在检查器里（本项目在 `00_原著/_consist.py` 的 `REF_EXEMPT`），不是按目录自动放行——因为自动放行等于这条规矩不存在。

**新增文件**：不在豁免名单里的，缺声明就红。想绕过去只能改代码，改代码要过审。

**豁免不是冻结**：改到哪份提示词，就顺手把那份迁完。豁免名单只保护「今天没碰它」的文件，不保护「明天要改它」的文件。

## 六、四条反例（都是真发生过的，抽象掉项目细节）

| 反例 | 当时写了什么 | 出来什么 | 病根 |
|---|---|---|---|
| 漏 `STYLE_REF` | 头肩肖像，只挂了人物图，正文描述了五官与构图 | 日式厚涂柔光——画风完全不是要的那档 | 没声明画风，模型用默认；**模板里没有画风段时，缺声明不会被察觉** |
| 参考图兼职 | 同一张图既当人物又当画风 | 姿态、构图、光线全被继承 | 规则 1 |
| 合并说法 | 「参考这几张图，保持一致性」 | 三张里最完整的那张赢 | 规则 2 |
| 单层硬塞 | 单图平台挂两张 | 构图被第一张锁死 | 规则 3 |

**第一条最隐蔽**：它不出错、不报错，只是安静地给出一个「还算好看但不对」的结果。所以 R1 才要查「整行不许省」——省掉的那一行，看起来像没需求，实际是没声明。

## 七、和 style_lock 的分工

- **本文件**：规定「谁管什么」。稳定，跨项目不变。
- **`styles/<项目>.style_lock.md`**：规定「这个项目的画风具体是什么」。每个项目一份，提示词里**原样引用，不许改写**。

改风格只改 style_lock，不动模板；换项目只换 style_lock，不动模板。

**为什么不许在提示词里改写 style_lock 的那串**：一旦允许改写，同一个项目就会出现两套风格串，出图对不齐时无法判断是「风格串不对」还是「这次抽歪了」。风格串只能有一个源头。
