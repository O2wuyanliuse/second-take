# 公库维护方法

> **English summary:** This is the operating manual for the repository itself: how a release is cut, which mistakes have already been paid for, and what the machine enforces.
> Release order is **tag first, then `master`**. The tag-triggered check reads the tag's own tree; pushing `master` first turns master's CI red on criterion 2, because the remote's newest tag is still the previous version.
> Before tagging, `tools/release.py` must leave `git status --porcelain` empty, and `VERSION` = `latest.json.version` = the tag name must all agree.
> §9 is the rule change log and it is **append-only**. Any commit touching `gate/`, `packaging/`, `tools/`, `scripts/` or `.github/` must add a §9 entry in the same commit, or say `[no-procedure-change: reason]` — `tools/check_maintenance.py` enforces this in CI.
> The Chinese text below is normative.

## 一、这个仓库是什么、不是什么

**是**：一套「从原文到成片」的方法层——判据、检查器、台账规则、提示词规则。
`gate/` 是各项目通用的检查器，`packaging/` 是打包与脱敏工具，`tools/` 是维护脚本，
`tests/` 是**本库自己的**用例（32 条，CI 跑 `python -m pytest -q`）——它测检查器有没有牙，
不测任何项目文件，所以项目改名不会让它红。

**不是**：不是装上就出片的产品，不含任何作品正文、设定集、素材文件。
按设计不含项目内容，所以门禁里有 15 项会「跳过」——**跳过不是绿**，它只说明
「本库没有那个对象」，`gate/_gate.py` 会把这个覆盖率印在每页末尾。

## 二、发版五步

发版是**唯一会改变 `VERSION` / `latest.json` / tag 的动作**。三处必须同源。

### 1 备料：CHANGELOG 两栏

`tools/release.py` 会机器判这几点，不过不给发：

- 有 `## vX.Y.Z · 日期` 节
- `### 对你有影响` **1–3 条**，每条去标记后 **≤30 字**
- 禁词：`重构`／`优化`／`修复若干`／`底层`／`架构`／`性能提升`／`若干问题`／`体验更佳`／`稳定性增强`
- 条目里不许出现 commit hash
- 有 `### 没动什么` 或 `### 内部`

### 2 先 dry-run，再真跑

```bash
<python> tools/release.py --version X.Y.Z --channel stable --severity normal --dry-run
<python> tools/release.py --version X.Y.Z --channel stable --severity normal
```

它一次写三处并提交：`VERSION` → `latest.json` → 一次提交（带 `SIGNED-BY: <本仓 user.name>`）→ `git tag -a vX.Y.Z`。失败自动回滚（`tag -d` ＋ `reset --soft` ＋ 还原文件）。

### 3 打包

```bash
git archive --format=zip --prefix=second-take-X.Y.Z/ HEAD -o ../second-take-X.Y.Z-win.zip
```

**前提**：工作区 0 脏，且 `HEAD` 就是这次要发的提交。

**`--prefix` 不能省**：zip 顶层目录名要与 `pack_urls` 里的资产名对上，否则用户解压出来是一地散文件。

**只出一个包。** 包里是纯文本与 Python，没有二进制，与平台无关；资产名里的 `-win` 是历史命名，不是平台限制。为「平台齐全」再造两个同内容不同名的 zip，等于拿 673 KB 换一个好看的矩阵——`latest.json` 的 `pack_urls` 也只会记一个。

### 4 三项手查

本库**不用**包校验器整体。`packaging/_verify_package.py` 面向另一种发行包：它要
`从这里开始.txt`／`使用说明.txt`／`00_原著/` 那套结构，对本库快照跑会报一串「缺 X」
——**那不是假绿，是一堆不适用的红**，别拿它当门。

**但它有一条判据跨仓通用**——`V11 包里没有这台机器的坐标`。这一项与本库结构无关，
只问「包里有没有解析得出来的盘符路径」。0.5.0 就是靠它抓到 5 处并修到 0。
用法：解包后跑一次，**只看 V11 那两行**（`✅ 扫 N 个文本文件，0 处…` ／ `✗ …（盘符绝对路径）`）。

手查三条：

```bash
<python> - <<'PY'
import zipfile, subprocess, json, hashlib
p = '../second-take-X.Y.Z-win.zip'
z = zipfile.ZipFile(p)
names = [n for n in z.namelist() if not n.endswith('/')]
tracked = [t for t in subprocess.run(
    ['git', 'ls-tree', '-r', 'HEAD', '--name-only'],
    capture_output=True, text=True, encoding='utf-8',
    check=False).stdout.split('\n') if t.strip()]
media = [n for n in names if n.lower().endswith(
    ('.mp4', '.mov', '.zip', '.png', '.jpg', '.jpeg', '.psd'))]
print('文件数', len(tracked), len(names), '差', len(tracked) - len(names))
print('媒体', len(media))
print('版本', json.loads(z.read('second-take-X.Y.Z/latest.json'))['version'])
print('sha256', hashlib.sha256(open(p, 'rb').read()).hexdigest())
PY
```

期望：**差 = 0**（清单是唯一真相源，没有 export-ignore 抵扣）；**媒体 0**；**版本**等于这次要发的版本。

### 5 先推 tag → 建 release → 最后推 master

顺序不能反，两个方向各撞一个坑：

```bash
git push origin vX.Y.Z      # ① 远端 tag 先就位，指向正确
                            # ② 网页建 release：tag 从下拉里【选】已存在的 vX.Y.Z，上传 zip
git push origin master      # ③ 用户这时才看到新版，而资产已经就位
```

- 先建 release 再推 → GitHub 会拿远端旧 HEAD 现场建 tag（坑 13）
- 先推 master 再建 release → 会有一段 `pack_urls` 指向不存在资产的 404 窗口

### 6 四条核验

```bash
git ls-remote --heads origin master          # 应等于本地 HEAD
git ls-remote origin "refs/tags/vX.Y.Z^{}"   # 应解引用到同一个提交
```

- 仓库的 `master/latest.json`（raw 地址）→ `version` 是新版
- 下载地址 302 到资产域名（不是 404），`Content-Length` 与本地 zip 字节数一致

### 7 两张「不进仓库」的表，分工不同

| 表 | 进仓库 | 改它的代价 | 放什么 |
|---|---|---|---|
| `.gitignore` | 是 | 一次提交（发版期还要挪 tag） | 对**所有人**都成立的忽略：素材、`__pycache__`、`.env`、`reports/` |
| `.git/info/exclude` | 否 | 零 | 只跟**这台机器**有关的：目前是打包输出 `dist/` |

`dist/` 放在 `exclude` 是权宜——它对别人其实也成立，但为一条忽略规则在发版期制造提交、进而挪 tag，不划算。**下次正经改 `.gitignore` 时顺手把它挪进去**，别单独为它发一次版。

判断标准一句话：**这条规则对别人也成立吗？** 成立写 `.gitignore`，不成立写 `exclude`。

## 三、坑（每条都是真踩过的）

**1｜Windows 上 tag 大小写会互相覆盖**
`git fetch --tags` 之后，远端的 `V0.4.0` 会**顶掉**本地 `v0.4.0`——NTFS 大小写不敏感，两个 ref 落到同一个文件。
症状：`git rev-list -n1 v0.4.0` 指到一个你没想到的提交。
处置：推 tag 前必须 `git rev-list -n1 <tag>` 核实际指向；别信 `git tag -l` 的名字。

**2｜GitHub 建 release 会自动把 tag 写大写**
建 release 时 tag 栏如果空着或随手打，GitHub 可能落成 `V0.4.0`；而 `latest.json` 里写的是小写。
症状：`/releases/download/v0.4.0/...` 返回 **Not Found**，但资产明明在。
处置：tag 栏**手打小写**；已经错了就去编辑 release 换 tag（编辑时别碰 tag 下拉以外的字段，见坑 3）。

**3｜编辑 release 时动 tag，正文可能被清空**
0.4.0 那一轮改 tag，正文被清成两行版本号。
处置：改 tag 前先复制正文；或改完立刻检查正文还在不在。

**4｜`release.py` 曾经只写文件不提交**（2026-11-20 已修）
症状：它打印「✓ 三处已同源」，实际 `VERSION`／`latest.json` 挂在工作区，tag 指向**上一个**提交，`git checkout vX.Y.Z` 拿到旧版本号。
处置：真跑后必须 `git log --oneline -1` 看到一条 `release X.Y.Z：…`；看不到就是没提交。

**5｜自带包校验工具验不了 `git archive` 的产物**
它要的是另一种发行包的结构（启动说明 + 版本目录）。拿它对整仓快照跑，只会得到「绿的假通过」。
处置：本库只用 §二·4 那三项手查。

**6｜`_pr_guard.py` 裸跑会等 stdin**
非 tty 环境下读 diff 会一直等 stdin，表现是超时（rc=124），而超时按未判算。
处置：用 `--range HEAD~1..HEAD` 或 `--file pr.diff`；已补防御——非 tty 且无 `--range/--file` 时直接 rc=2。

**7｜`_leakscan.py` 必须有词表，否则 rc=2**
骨架侧不给词表就是 2，这是设计（词表属于项目，不属于通用库）。跑出 2 不要当故障。
~~2026-11-21 起本库自带一份 `packaging/public_denylist.txt`，CI 用 `--deny` 跑，不再依赖外部词表。~~
**→ 2026-11-21 晚改回「词表不在库里」**：它必须写出要禁的词，留在库里等于自泄一次。CI 从仓库 secret
`PUBLIC_DENYLIST` 注入到 `.ci/denylist.txt`（已 gitignore）再 `--words`；本地自己给 `--words`。

**8｜`_triage.py` 词表不全曾给 rc=0**（0.4.1 起改 rc=2）
症状：明明「拒绝开工」，退出码却是 0，拿它写 CI 的人会当成通过。
处置：已改；若在旧版本上跑，看到「⛔ 拒绝开工」时别信退出码。

**9｜网页抓取有 15 分钟缓存**
同一个 URL 反复抓，第二次可能拿到旧结果（曾因此把已修好的 release 页判成 404）。
处置：加 `?t=<时间>` 换 key，或换端点（`/releases`、`/releases/expanded_assets/<tag>`）。

**10｜含内容的仓库永远不要 `git archive` 发版**
`git archive` 打包的是 HEAD 的**全部跟踪文件**。仓库里一旦有正文定稿、媒体件，archive 出来就是把它们打进 zip。本库按设计不含内容，所以能用它；**换了任何含内容的仓库，这条就翻面**。

**11｜推 tag 之后又想改指向**
已推送的 tag 不要随手 `-f`。真要改：先确认没有用户拿到过那个 tag，并在提交/回执里写清「原处 → 现文」。

**12｜钩子自报的项数会比 `_CHECKS` 多**
提交时钩子会按暂存内容**自加检查**：有新增 `.md` 就多跑一次孤儿件检查。所以「共 N+1 项」不是第二真值，是 N 项加那一步。
处置：别去查，查了白花五分钟。

**13｜网页建 release，tag 会指到「远端还没追上的那个 HEAD」**（2026-11-21，0.4.3 踩的）
症状：release 页面挂着 `v0.4.3`，旁边那串提交号却是上一版的；`git ls-remote origin "refs/tags/v0.4.3^{}"` 指过去，那个提交里的 `VERSION` 还是 `0.4.2`——**资产是对的，tag 错了一整版**。
原因：**tag 不存在时，GitHub 会拿远端默认分支的 HEAD 现场建一个**。而发版那一刻本地刚提交完、master 还没推，远端 HEAD 停在发版前那笔。
处置：先推 master 追平 → `git push -f origin refs/tags/vX.Y.Z` 覆盖指向（前提同坑 11）→ 核 `^{}` 解引用。
**核验口诀**：release 页面那串短号，必须等于 `git rev-parse --short HEAD`。

## 四、边界（写死，不留解释空间）

- **不** `git commit --amend` 已推送的提交；**不** `git push --force` 分支
- **不**手改 `latest.json` / `VERSION`——发版记录一改，这次发布就不算数
- **不** `git add -f` 媒体件
- **不**在资产上传之前推 master
- 一次提交只做一件事；message 带 `SIGNED-BY: <本仓 user.name>`
- 哪一步卡住就停下说卡在哪，**不绕**——绕一次，下次得再写一份清账清单
- **不**把「我这儿能跑」当验收；跑不了就写「未核」

  ```bash

  ```

  **任何禁用词表都必须写出它禁的词，这是定义、不是漏检。**所以别把一条
  「理论上归零、实际永远 1」的 grep 当门——那种门第一次跑就会被当成噪声忽略，

机器兜底：CI 跑 `tools/check_maintenance.py`——**改了 `gate/`、`packaging/`、`tools/`、`.github/` 任何一个，就必须同时改这份文件**，否则提交信息里要写 `[no-procedure-change: 理由]`。
它**逐个提交**判（v1.8 起）：改的文件与该提交自己的消息必须对得上，**下一条提交的免责标签不能替上一条免责**。多个提交一次 push 时，这是唯一还看得见洞的姿势。

## 八、代码硬约束

这七条是「去 AI 味重构」定下的写法尺子，主角在这里，机查在 `packaging/_style.py`（不进包）。

1. 所有函数（含 main）≤80 行；main 只编排。确有历史原因的豁免只认 `docs/maintain/_style基线.md` 中精确的「相对路径:函数名 — 理由」。
2. 模块 docstring ≤15 行；表格／叙事／事故史进 `docs/maintain/`，代码留一行指针。
3. `except Exception／BaseException`（含其元组）若只有单一 `pass`／`continue`／`return None 或常量`，必须在出口所在行写 `# 吞：<非空理由>`；多句处理不报，具体异常类型不适用此条。
4. 同一 helper 不许跨文件抄第二份；豁免逐文件判断，只认函数开头注释行 `# 故意重复：<非空理由>`，其他副本不因同组有标记而豁免。
5. 检查项不许静默删；删一个须同提交在 `docs/maintain/` 登记理由＋替代。
6. 行为冻结：pytest 原 125 条全绿且断言口径不改（允许新增用例，总数 ≥125）、gate 四数（绿3/跳15/提1/阻0）不变、evidence 结论不变、包内文件数按白名单走。
7. 新增进包文件过白名单一行＋理由；打包计数 == 清单有效项。

跑法：`python packaging/_style.py`。CI 里也有这一步。
