# 06 · 数据采集与迭代规范（开源 / 上传 / 采集 / 迭代）

> **路径说明**：本文出现的 00_原著 下具体文件名都是**项目实例**（示例、产物位置），带走后不存在是正常的；命令块里的脚本调用是**位置约定**，位置不变就能跑。详见 `11_分发说明_v1.md` §四。

> **读者**：两者
> **层**：**通用层**——整份可搬给别的项目。采什么、怎么埋点、迭代闭环怎么收——方法层，不绑题材
> 定位：管「这个 Agent 开源后，怎么采集真实使用数据、怎么用数据把 Agent 迭代得更普适」。
> 来源：2026-10-27 作者提出"文笔采集环节要开源后采集才能普适化"，本层把这件"还没做、但要做对"的事，先想透、写成可执行规范。
> **这层不绑任何一部作品**，任何"想靠外部数据进化的 Agent"都适用。

## 〇、先立一个总原则（别急着开源）

**顺序是：先定采什么 → 再脱钩打包 → 埋采集点 → 回流迭代 → 最后才开源。** 反着来，会拿到一堆 star 但零数据回流。

四步一句话：
1. **定采什么**：采"协作成败信号"，不采"文笔样本本身"（见第一节）。
2. **脱钩打包**：把绑死原项目的内容剥掉，做成可复用专家包（见第二节）。
3. **埋采集点**：在流程节点埋结构化日志，靠格式强制、不靠自觉（见第三节）。
4. **回流迭代**：回流数据进「待打磨区」，走已有的归类流程升版本（见第四节）。

---

## 一、采什么（最关键的一步，想错全盘皆输）

### 核心红线：不采「文笔样本」，采「协作成败信号」

> 依据：第 16 条「文笔提炼要分层」——**单一作者提炼不出通用规律，通用规律靠多样本统计，不靠单一作者凭空提炼。**

- **文笔样本（手法、意象、写法偏好）是「每个作者私有、绑死作品」的**，采一堆陌生人的手法样本，反而会污染"通用层只放中性结构认知"的原则。所以开源后**不采集别人的文笔样本**。
- **真正值得采、且能迭代 Agent 的，是「协作过程的成败信号」**：哪类改写被采纳、哪类被返工、哪个环节卡住、哪种分镜方式好用。这些是**跨作者、跨作品都成立的**，能直接反哺规则层/流程层。

### 该采的四个信号（结构化字段）

| 信号 | 采什么 | 为什么有用 |
|---|---|---|
| **采纳率** | 某次改写/补写，作者是"直接采纳"还是"返工" | 反哺规则层：哪种写法成功率高低 |
| **返工原因** | 返工时作者指出的问题类型（视角错/加功能/惯性修辞/另起炉灶……）。**更硬的形态是"逐处改动"——见 `四·补一 文笔校准`** | 反哺五病根分类，发现新病根或旧病根高频复发 |
| **环节卡点** | 哪个流程环节（体检/审校/分镜/落盘）最容易卡、作者最常手动介入 | 反哺流程层：哪里该加硬闸、哪里该简化 |
| **分档偏好** | 省事档 / 极致档的用户，各自在哪个环节流失、哪个环节满意 | 反哺第 0.5 条分档：两档的默认行为怎么调 |

### 明令不采的（防污染）

- ❌ 不采具体文笔意象、写法偏好（那是项目私有，不是通用规律）。
- ❌ 不采角色设定、情节伏笔（那是作品私有，无迭代价值）。
- ❌ 不采可识别作者身份/作品隐私的信息（采集必须匿名化）。

## 二、怎么上传（脱钩 → 打包成专家包，不是先裸开源）

### 第一步：脱钩（把绑死原项目的内容剥出来）

打包前，逐层过一遍"能不能脱离这部小说成立"（第 0 条标准），能留的留、不能留的剥到项目私有：

| 层 | 能脱离（保留） | 绑死项目（剥出） |
|---|---|---|
| 01 规则层 | 叙事铁律、视角逻辑、三元验证 | 任何引用了具体角色/设定的例句 |
| 02 流程层 | 状态机、四字段、开工清单、备份纪律 | 具体锚点、具体 md5、具体文件路径 |
| 03 方法论层 | 五病根、三错、中性放行 | 具体意象举例 |
| 04 分镜标注 | 标注规范本身 | 具体场景的分镜实例 |
| 05 归档规范 | 前缀、时间戳、分区 | 具体文件名 |

**脱钩产出**：一份"通用版 Agent 框架"（可复用）+ 一份"项目私有层"（留在项目，不随 Agent 走）。

### 第二步：打包成专家包（agent 平台通道）

- 用 `expert-manager` 能力，把脱钩后的框架 + 配套脚本（`_lint.py`、`_gen_diff_view.py`）转化成一个**可安装的 Expert**。
- 配套脚本作为专家的"工具"带进去，不让用户自己跑命令行。
- **先闭环、再开源**：专家包在 agent 平台里跑顺、验证"别人真能用、真省事"之后，再考虑开源到 GitHub。

## 三、怎么采集（埋采集点，靠格式不靠自觉）

> 依据：memory 里"靠自觉靠不住"的教训，采集必须靠格式强制，不靠用户主动反馈。

### 采集原则

- **采集点嵌在流程里，随流程自动产出**，不额外增加用户负担。
- **结构化字段**，不采自由文本（自由文本无法统计）。
- **用户可选择是否回传**，不静默上传（尊重隐私，也符合开源社区习惯）。

### 埋点位置（对应 02 流程层的节点）

| 流程节点 | 埋什么 |
|---|---|
| 改写/补写交付后 | 作者"采纳/返工"的选择 + 若返工，返工原因分类 |
| 审校视图圈定后 | 保留/回退 的逐条结果 |
| 收口落盘后 | 本次是否触发了断点、哪个环节耗时最长 |
| 分档判定后 | 用户选了省事档还是极致档 |

### 产出格式（一条记录示例）

```json
{
  "agent_version": "0.1.0",
  "event": "rewrite_feedback",
  "signal": "rework",
  "reason": "视角错",        // 对应五病根/三错分类
  "tier": "极致档",
  "anonymized": true
}
```

### 回传方式（成本递增，先做第一条）

1. **结构化日志导出**（先做）：把采集点记成一个 `.jsonl` 文件，用户选择导出/回传给你。低成本、够用。
2. **用户主动反馈入口**（辅助）：在 Agent 里埋一个轻量反馈点，兜底捕获日志没覆盖的主观感受。
3. **平台级匿名统计**（后做，需后端）：做成专家包后，借云服务能力做匿名使用统计。**等"采什么"验证清楚再上，别先建平台。**

## 四、怎么迭代（回流 → 待打磨区 → 升版本）

> 依据：你已经有"待打磨区"（迭代入口）和"维护约定"（归类流程），本层只补"外部数据怎么接进来"这一环。

### 迭代闭环（五步）

1. **回流**：采集数据回传，进入一个独立的"外部信号队列"（不直接进规则层，先隔离开）。
2. **归因**：把信号归类到已有框架坐标——是"五病根"里的哪个？是"三错"里的哪种？还是发现了**新病根/新规律**？
3. **进待打磨区**：凡"看起来跨作者成立、但还差多样本验证"的，登记进 `待打磨区_方法论台账.md`，标"想进哪层 + 还差多少样本"。
4. **走维护约定归类**：按 README 维护约定的固定流程——判状态 → 判归属（能/不能脱离作品）→ 判层 → 冲突提示作者 → 报去向。
5. **升版本**：一条方法论定稿落位后，Agent 版本号 +1（语义化版本，见下）。

### 版本管理（语义化版本）

- **主版本（X.0.0）**：新增/删除一层，或第 0 条级别的顶层原则变更。
- **次版本（0.X.0）**：三层内部新增一条铁律/流程/姿态。
- **补丁（0.0.X）**：措辞修正、例句替换、采集字段微调。

### 防自我闭环（最重要的一条）

> 依据：第 16 条"禁止自我闭环迭代"——AI 拿自己的产出当样本会越迭代越偏。

- **迭代的样本，必须来自外部的、多样的、真实的用户数据**，不是 AI 自己生成的内容。
- **单一来源的样本不足以立一条通用规律**：一条新规律，至少要观察到**多个不同作者/项目**里重复出现，才能从"待打磨区"升到"已定稿"。
- **只有一个项目的数据，只能得"这个项目的习惯"，得不了"跨作者的规律"**——这正是本层存在的意义：用开源后的多样本，把"单一项目习惯"验证/淘汰成"通用规律"。

## 四·补一、文笔校准：把「返工原因」变成可执行规则（**待验** · 2026-10-29）

> **状态：待验。** 方法设计成立，但**尚未跑过一次完整的改稿对照实验**。按本项目纪律「没跑过的不当已定」，这一节在验证前**不得当成"已经能用"引用**。
> **来源**：作者 2026-10-29 02:20 点破——续写最难的不是逻辑（框架会填），是**文笔统一**：「你不说人话，或是为了自洽，你写的东西过于方便自己通过；但读者容易一眼人机」。

### 为什么单列一节

第一节已经在采「返工原因」，但那一格采的是**作者口头说的类型**（视角错／加功能／惯性修辞）。这是**弱证据**：

- 弱证据：作者说「这句不对」——我记下"属于加功能"，下次注意。
- 强证据：作者把「他不禁心头一紧」改成「后槽牙咬得咯吱响」——**这是可执行的规则**。

**本节要做的，就是把弱证据升级成强证据：采的不是"哪里错"，是"改成了什么"。**

### 三个入口（按成熟度分流，不强制）

> 接第 0.5 条分档。**同一个方法，不同的人从不同的门进来。**

| 级 | 用户做什么 | 耗时 | 采到什么 | 适合 |
|---|---|---|---|---|
| **L1 标记级** | 只标「这几句读着不像我」，**不用改** | 3–5 分钟 | 位置 ＋ "不对劲"的位置 | 刚学写作的、没时间的 |
| **L2 改稿级** | 直接在上面改 | ~15 分钟（老手更短） | 逐处「原 → 现」＋ 改法类型 | 有判断力的写手 |
| **L3 跳过** | 不做，接受「像但不是我」 | 0 | — | 省事档 |

**L1 不是"降级版"，是"低门槛版"**——它解决一个真门槛：**不会改的人，也会觉得不对劲。** 那就别要求他会改，只采集"哪里不对"，改法由我推、下一轮再纠。

### 采的是什么、不是什么（守住第一节的红线）

- ✅ **采改法**：这一处从 A 变成 B、为什么。**这是跨作者都成立的结构认知。**
- ❌ **不采意象与手法偏好**：这位作者爱用"心悸从脊梁往上爬"——那是项目私有，不进通用层。
- **区别一句**：采「怎么改」是结构，采「用什么词」是私有。

### 基线必须现算，不许给死值

同一个人群写法差异极大。实测：本项目作者原文「四字整句」密度 0.47，AI 稿普遍 1.8–3.8 倍。

**所以：**

- **指标项通用**（四字堆叠、解释性连词、副词"地"、句长变异、对话占比、短句率、段均长）
- **阈值不通用**——每次校准**先算这个作者自己的基线**，再拿新稿去比
- 任何人拿一套固定阈值去套所有作者，都是在制造新的"人机味"

### 待验清单（验通了才允许把"待验"改成"已验"）

1. **改法规则能不能稳定提炼？** 3–5 次对照之后，归纳出的规则是不是收敛的，还是每次都不一样？
2. **提炼出来的规则，下一次续写真的改善了没有？** 不验这一条，就只是自我感觉良好。
3. **L1 标记推出来的改法准不准？** 只标"不对劲"、不改，我推的改法作者认不认？

> **第一次对照已跑通（2026-10-29 03:19，样本 1 段）**。初步结论有三条，都可复用：
> 1. **AI 版比作者版短 29%**（563 → 728 字）——**文笔不像的原因不是啰嗦，是"该有的细节没写"**。这条推翻了"AI 爱注水"的旧假设。
> 2. 归纳出 **5 类改法**：具体 vs 抽象（评价词改物象／比喻改动作）／缺的因果链与现场（动作前因、光源、旁人、工具用法）／节奏不许切碎／口语层往土了写／声音质感与反讽命名。
> 3. **每千字密度类指标在 500 字样本上失效**（全归零）——这类工具只适合**整卷体检**，不适合逐段校准。**逐段只能靠人工对照。**
>
> **样本量 1 段，不足以称"稳定"。** 项目级的改法与实例归项目层，不在这里——**这里只留结论**（分层原则）。

### 防自我闭环（接第四节那条）

**不能用「AI 自己觉得像了」当验证。** 唯一判据是作者本人：他看到新稿，说的是「这句我也会这么写」，还是「不像」。

> 这条尤其要紧——因为「人机味」最诡异的地方就是：**写的人读不出来，读的人一眼就看出来。** 让写的人自评，等于让病人自己签出院单。

### 成本要说实话

- 单次：L2 约 15 分钟（老手）／L1 约 3–5 分钟
- **一次不够**。要覆盖动作／对话／心理／异象几类，估计 3–5 次
- 累计约 2 小时，换来后面每次续写都贴本人

**这不是"花小力气"，是"一次性预付款"。** 好处是这笔账只付一次，而且付给的是**规则**，不是 AI 的记性。

## 五、这一层跟其它层的关系

| 层 | 本层怎么接 |
|---|---|
| 第 0 条统一门阀 | 采集数据是"外部投影"，**唯一真相源仍是项目目录权威文件**，采集信号不得反过来污染真相源 |
| 第 0.5 条分档 | 采集"分档偏好"信号，反哺两档默认行为 |
| 第 0.6 条建模/施工 | 采集数据本身是"建模"重活的一部分，一次采透、固化、复用 |
| 01 规则层 | 采纳率/返工原因 → 验证或新增叙事铁律 |
| 02 流程层 | 环节卡点 → 增删硬闸、调清单 |
| 03 方法论层 | 新病根/新姿态 → 进五病根、进核心姿态 |
| 待打磨区 | 外部信号先进这里，不直接进三层 |

## 六、为什么这层要"先想透，再动手"

- **采错东西 = 采回来一堆污染通用层的噪音**，比不采更糟。
- **顺序错 = 先开源拿到 star 但零回流**，白忙。
- **这层本身就是"先踩坑填坑"的 Agent 本质**：把"开源后才发现采错了"这个必然要踩的坑，提前在这一层踩完。

> **一句话**：先把"采什么、怎么脱钩、埋哪、怎么迭代"想透，再谈开源——否则开源不是进化的起点，是失控的起点。
